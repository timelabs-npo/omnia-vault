# Requirements register after the technical reset

12 September 2026 · Requirements refinement only · No implementation approval implied

The latest user direction takes precedence over the earlier specification. All macOS prototypes, mockups, pane layouts, labels and demonstrations are discarded as the product baseline. Their source and results can explain earlier findings; they do not establish the required design or prove readiness. The current task is to refine the actual LIT001 chain and its technical contracts before crafting anything.

This register preserves accepted outcomes from the conversation and the earlier continuity specification and provider registry. Those documents contain proposals as well as decisions. Their architecture, old P0 labels, polling intervals and resource limits are not automatically accepted requirements. The questions below are verification work or unresolved decisions, not requests to repeat choices the user has already made.

## Current critical work: useful network continuity

| ID | Accepted requirement | Verification question | Decision or evidence still needed |
|---|---|---|---|
| REQ-NET-01 | Make the user's real model applications usable through the intended connection chain. | Does each agreed application complete its real operation through the identified path? | Exact application versions, destinations, protocols and operation-level success criteria. An HTTP response from one host is insufficient. |
| REQ-NET-02 | Give the SCION alternative the intended priority, with the existing VPN as the fallback where needed. | Can a controlled new connection use the preferred path, and can a failure produce the agreed fallback? | Who owns the routing or proxy policy; supported application scope; trigger, timeout and recovery behavior. A service-order change alone does not establish this behavior. |
| REQ-NET-03 | Protect ongoing work when checking or changing connection policy. | What happens to an active model response or session during path loss, recovery and a policy change? | Distinguish new connections from established TCP/QUIC sessions. Define acceptable interruption, reconnection and user action; seamless migration is not assumed. |
| REQ-NET-04 | Separate path availability, selected policy and actual useful traffic. | Can evidence identify the policy and path that carried a specific successful application operation? | Correlation and observation at each relevant boundary. A green daemon, listening port, SCMP reply or button acknowledgement is not application delivery. |
| REQ-NET-05 | Start from the actual SCION and GNS3 mechanics and installed LIT001 chain. | Are each component's role, version, configuration, interface and dependency established from the real chain? | Exact inventory and supported deployment combinations. C-FFI linkage or a simulated injection log does not prove a working transport or memory-safety guarantee. |
| REQ-NET-06 | Keep macOS as the primary working environment and Windows/WSL as the helper in the present setup. | Can the helper perform its assigned work without taking over the user's main desktop workflow? | Which functions require the helper at runtime; Windows, WSL and virtualization capabilities and permissions. Do not assume interchangeable Mac and Linux kernel behavior. |
| REQ-NET-07 | Diagnose failures at the boundary supported by evidence. | Can a failed operation be localized to the sender, host boundary, helper, SCION path, gateway or destination? | Bounded diagnostics, effective firewall policy and capture permissions. No response alone does not identify a firewall fault; one-way receipt is not a round trip. |
| REQ-NET-08 | Make connection controls perform real, bounded actions with observable outcomes. | For each control, is the requested action followed by a readback and a functional check, including failure or uncertain outcome? | Allowed actions, preconditions, timeout, duplicate handling and rollback. A saved setting must be distinguishable from an applied setting. |
| REQ-NET-09 | Accept the network workstream on reproducible evidence for the agreed workload. | Can another run reproduce normal use, path failure, fallback and recovery within the agreed limits? | Workload, duration, acceptable loss/interruption, latency and resource/cost budgets. Earlier user-reported network successes remain scoped evidence, not a general release certificate. |

## Product and engineering constraints

These constrain the first beta where the relevant surface or operation is included. They do not authorize building a new UI during this refinement phase.

| ID | Accepted requirement | Verification question | Decision or evidence still needed |
|---|---|---|---|
| REQ-UX-01 | Use plain, common English for product labels and instructions. | Can a user understand each action and result without knowing internal module names or metaphors? | Review the future wording against real tasks. Protocol and provider names may be necessary; internal component names are not navigation requirements. |
| REQ-UX-02 | Show Timelabs only in About or legal information. | Is the vendor absent from navigation, feature names and workspace or pane titles? | Product name is a separate decision. Earlier visible branding is not precedent. |
| REQ-UX-03 | A standalone work window must move, resize and minimize normally and be accessible by keyboard. | Can the user position the window, resize its content, minimize it and complete the workflow without a pointer? | Minimum usable size, focus order and accessibility checks. No fixed-position, non-draggable popup as the main workspace. |
| REQ-UX-04 | A tray popup is optional compact status; a real System Settings pane is native configuration. | Is substantial work available in a normal work window, and is any claimed System Settings integration an actual native pane? | Which configuration belongs in the pane. A desktop window that resembles System Settings is not an OS pane. Existing prototypes supply no layout requirements. |
| REQ-UX-05 | Show concise, useful state and controls, with evidence available when needed. | Does the surface help complete a task, and can each metric or status be traced to its source, scope and observation time? | Units, freshness limits, unsupported states and details presentation. Unknown, stale, failed and a valid empty result must remain distinct. No fabricated health, accounts or metrics. |
| REQ-ENG-01 | Keep the longer-term goal of independent installation and operation. | Can the intended deployment be reproduced without a developer checkout or accidental machine-specific dependency? | Proposed target: a self-contained Mac deployment, with the present Mac/Windows lab kept as a separate profile. Runtime dependencies and platform support still need proof. This is not proof that the Mac can already work without the helper. |
| REQ-ENG-02 | Make the actual LIT001 chain reviewable before implementation. | Does every required operation identify its component, input, output, dependency, failure behavior and verification evidence? | The technical contract must define the actual chain. Do not inherit unverified prototype architecture or create additional layers merely to complete a diagram. |
| REQ-ENG-03 | Protect credentials and constrain privileged operations. | Are secrets absent from repositories and reports, and can each privileged action be tied to an explicit purpose and scope? | Authentication, credential custody, permissions and deployment ownership. Do not promise access that the OS or provider has not granted. |
| REQ-ENG-04 | Establish practical operating and release limits. | Are supported versions, resource use, costs, failure limits and release blockers measured and documented? | Numeric budgets and retention limits remain to be agreed. No claim of unrestricted OS access, infinite storage, universal availability or unproved cryptographic security. |

## Remaining accepted delivery requirements — still in scope

The user requested every listed provider for beta. Network continuity is the current critical workstream, not approval to narrow the beta release. All listed provider, sync and archive requirements remain in the requested scope until the user changes it. Each adapter or feature requires its own acceptance stage; a network-only milestone is not the full requested beta.

| ID | Accepted requirement | Verification question | Decision or evidence still needed |
|---|---|---|---|
| REQ-DATA-01 | Support iCloud Drive, Google Drive, OneDrive, S3/MinIO, Mac folders, Windows folders and NAS. | For every provider, are discovery, permitted reads/writes, offline behavior and failure handling verified on the supported platform? | API and runtime versions, authorization, folder hydration, NAS protocols and endpoint capabilities. Do not silently replace this scope with two providers or assume identical APIs. |
| REQ-DATA-02 | Synchronize selected folders in both directions and preserve conflicting versions. | Do independent edits retain both versions, including after an offline period or interrupted transfer? | Change detection, identity, metadata coverage, reconciliation and conflict resolution. Clock order alone must not silently choose a winner. |
| REQ-DATA-03 | Handle deletion and incomplete scans explicitly. | Can a missing permission, offline endpoint or partial listing occur without being interpreted as permission to delete the other copy? | User-selected deletion propagation, trash, retention and offline-peer policy. Broad archive coverage does not broaden the selected sync roots. |
| REQ-DATA-04 | Archive all user files with configurable exclusions, including otherwise overlooked work. | Does the inventory account for untracked files, Git stashes and other user work, and report inaccessible or excluded material? | Applied exclusions, consistency of files in use, snapshot scope, permissions and handling of secret material. Do not claim completeness when items could not be read. |
| REQ-DATA-05 | Use the existing storage and key scheme as the default for the private archive. | Can the current nonsecret profile references be bound to working storage, keys and a verified restore? | Exact bindings, encryption coverage, key custody, recovery and rotation. Missing bindings in reviewed documents do not mean the user's existing scheme is absent. No real credentials in the repository. |
| REQ-DATA-06 | Preserve history and prove recovery within actual storage limits. | Can selected files and versions be restored and verified after interruption or loss of a working copy? | Capacity, quotas, retention, integrity semantics, recovery objectives, storage and egress costs. History is not assumed unlimited; no source deletion based solely on upload acknowledgement. |
| REQ-OPS-01 | Provide useful resource and service monitoring without impairing work. | Are observations accurate for their host and scope, and does monitoring stay within an agreed overhead budget? | Necessary collectors, intervals, permissions and freshness. Earlier CPU/RAM/GPU cards and polling values are not required product features. |
| REQ-OPS-02 | Automate approved maintenance of owned services and permitted regenerable caches. | Does maintenance respect active work and verify the intended result before reporting success? | Ownership, busy/unknown guards, approved paths, retries and recovery. This is not general permission to clean user files, restart shared networking or disable filtering. |
| REQ-REF-01 | Use NDI as a reference toolkit only. | Are borrowed interaction principles clearly separated from runtime dependencies and delivery claims? | No NDI media integration is required for beta. Research references do not establish installed functionality or a mandatory implementation architecture. |

## Decisions to settle next

First establish the actual LIT001 chain and the application operation that defines success. Then resolve connection-policy ownership, treatment of existing sessions, failure and recovery limits, and the minimum evidence required to accept the network workstream. Keep the independent-deployment definition, complete provider plan, archive bindings and maintenance policy in the accepted scope with explicit acceptance stages. Provider, sync and archive acceptance remain required for the full requested beta. No pane, window, transport layer or adapter is to be implemented from this register alone.
